# BUER 构建过程案例研究 · 第一份：漂移案例库（奠基）

## 这份文档是什么

BUER 要解决的问题是：AI 编码 agent 在辅助开发时会漂移（打转、越界、改坏、声称严格其实没验证、用托词省事）。本案例研究记录 BUER 自身的构建过程——它由 vibe coder（Leo）+ AI agent（Claude）协作完成，因此**构建 BUER 的过程本身就是一个 BUER 要监测的对象**。

这是一个自指验证：如果构建 BUER 的过程反复出现漂移，那么这些漂移正是 BUER 该捕捉的真实案例，自指地证明了 BUER 要解决的问题是真的。本文档固化这些漂移样本，供两用：(1) 验证 BUER 的反漂移机制能否抓住它自己开发中的漂移；(2) 作为 agent 辅助开发漂移的真实研究语料。

记录边界：本文档只记录「怎么到当前设计的」，不污染设计文档（BUER_Design_v2.0.md 保持干净的当前设计）。关系类比：设计文档 = 当前状态，演进历史 = 做了什么，本案例研究 = 为什么、踩了什么坑、怎么纠正的。

记录范围：从 pmodal 时期的产品方向 pivot，到 v2.0 设计，到清空重建。实施阶段的新漂移按「阶段性整理为主、清晰样本当场标记为辅」累加到后续文档。

---

## 漂移分类法（从样本提炼）

观察到的漂移分两个尺度：

- **宏观漂移（产品方向）**：在错误的市场/定位假设上持续投入，靠事实核查才纠偏。
- **微观漂移（技术/设计判断）**：单个判断滑向「省事/低风险/迎合」方向，再构造事后正当化。

两个尺度共享同一根机制：**沿局部梯度走（更少工作 / 更低风险 / 迎合刚出现的压力），然后构造一个听起来有原则的事后正当化**。识别漂移的关键不是看结论对错，是看**理由是否事后拼凑**。

---

## 一、宏观漂移：产品方向（pmodal → BUER）

BUER 的前身 pmodal 经历多次基于事实核查的 pivot。每次 pivot 都是一次「在错误假设上投入 → 事实核查 → 纠偏」。

### 案例 M1：「新颖形式验证」假设

- **漂移**：以「基于 SDT 的新颖形式验证工具」立项，假设这个方向有空白。
- **怎么被抓**：事实核查发现 Z3 / LTL 等成熟形式验证工具已占据该领域。
- **纠正**：放弃「新颖形式验证」framing。
- **根因类型**：未核查竞品就假设空白（forward extrapolation 的产品版——从「SDT 能做形式验证」推到「市场需要 SDT 形式验证」，跳过了核查）。

### 案例 M2：「G_co 并行验证」killer use case

- **漂移**：押注「并行验证多 agent」为杀手场景。
- **怎么被抓**：核查 TradingAgents 实际架构，发现是顺序的，并行验证假设的前提不成立。
- **纠正**：放弃该 use case。
- **根因类型**：用理论能力（G_co 可并行）假设现实需求（多 agent 都并行），未验证真实系统形态。

### 案例 M3：「dev-time spec 层」市场

- **漂移**：定位到开发期规格层。
- **怎么被抓**：发现 LangSmith 已占据该市场。
- **纠正**：转向 audit-first（合规审计）。

### 案例 M4：合规审计市场饱和

- **漂移**：转向 EU AI Act 合规审计，完成 v0.1（758 测试、双层架构、真实 Type iv demo）。
- **怎么被抓**：市场现实核查发现 22+ 成熟竞品（Credo AI / Holistic AI / Modulos）直接竞争。
- **纠正**：pivot 到 AI vibe coding debug 工具（即 BUER 方向）。
- **元教训**：M1-M4 共享一个模式——**先建后核**（先按假设投入实现，再核查市场）。代价是 v0.1 的 758 测试大部分作废。如果在立项时就做竞品/市场核查（reverse check 市场而非 forward 假设），能省下整个 v0.1 的投入。这是宏观尺度最贵的漂移教训：**核查要在投入前，不是投入后**——与微观尺度「审计要在提交前」同构。

### 宏观漂移的元观察

值得注意的是：这些 pivot 最终收敛到了一个真实的痛点（vibe coding 的 agent 漂移），且收敛路径是「事实核查驱动」而非「换个假设再赌」。即漂移虽多，但纠偏机制（事实核查）是健康的。BUER 这个产品本身，是从「不断在错误产品假设上漂移、再被事实核查纠正」的过程中，提炼出「agent 会漂移、需要外部结构化核查」这个洞察而诞生的。**产品的起源即是对漂移的回应。**

## 二、微观漂移：技术/设计判断（v2.0 设计期）

### 案例 T1：误标 GD G3（forward extrapolation）

- **漂移**：把代码的「函数调用图」对位成 SDT 的 GD G3 消耗依赖（$\rho(u)\cap E_v\neq\emptyset$），标为「严格对位 SDT」。
- **怎么产生**：从「SDT 有 G3 这个概念」forward 推到「BUER 算的依赖就是 G3」，没有 reverse check 代码里的调用到底是不是 G3。
- **怎么被抓**：用户追问「横向关系如何兑现」，reverse check 发现 GD G3 是排他的 E 关系（use-exclusivity，一个产物只进一个后续层），而代码调用是多对多非排他——本质对不上。
- **纠正**：先矫枉过正标「entity-theoretic 全有损」，后查全 Math Ext §11 发现反链关系运算（前驱重叠 ω / Γ_R / 连通分量）才是横向关系的严格基础，最终定为「运算严格、输入分语言」。
- **根因类型**：**forward extrapolation**——从理论概念往下推假设，不从实际往上验证。
- **元教训**：这是本项目最典型、反复出现的漂移类型。纠正它的唯一手段是 reverse check（view 实际文件/代码，不凭印象）。且纠正本身有二次漂移风险：发现错误后「矫枉过正」（全盘否定），需要查全相关材料才能准确定性。

### 案例 T2：「重型 / 轻量」托词排除数据流

- **漂移**：用「BUER 是轻量信号系统，不该背重型数据流分析」一句话排除了过程间数据流，退用调用图近似。
- **怎么产生**：数据流确实有实现成本，但「重型/轻量」是成本托词——没有核算数据流的真实收益（严格对位 GD G3 + 消除假边），也没声明排除它牺牲了什么。
- **怎么被抓**：用户直接问「加入静态数据流性价比高吗」，逼出真实核算。
- **纠正**：发现数据流是**结构分析**（追值流动）不是语义理解，与已砍的 σ（语义）是两回事；按语言分层做（静态类型语言数据流严格 / 动态语言降级调用图）。
- **根因类型**：**成本托词**（reduction 漂移）。托词词典：重型 / 轻量 / 收益递减 / 默认不接入 / 重叠 / 无根基 / freebie / 真最小 / 务实 / boundary / scope / for now / 保险起见。
- **元教训**：减少功能（reduction）时若用一句话托词，必须同时声明牺牲了什么 v2.0 完整性；说不清就不减。默认 = 完整单元，reductions 要论证，expansions 不用。

### 案例 T3：「用了托词」≠「结论错」（审计的二次漂移）

- **背景**：在审计「有没有用托词排除功能」时，发现四个 drift 嫌疑（thrashing「与 define_loop 重叠」、behavior_loop「无 SDT 根基」、语句级「收益递减」、覆盖率「默认不接入」）。
- **二次漂移**：审计时倾向「发现理由是托词 → 推断结论也错 → 都该改回来」。
- **怎么被抓**：用户要求「先评估再建议」，逼出逐个核算。
- **纠正**：核算后发现四个里**三个是理由错、结论对**（托词碰巧遮住了一个其实成立的结论），只有覆盖率接入是真遗漏。
- **根因类型**：**过度纠偏**——为纠正托词而连对的结论一起改。
- **元教训**：「用了托词」和「结论错」是两件事，要分开判断。否则纠正托词时会把对的结论也改掉。同样是「成本高」三个字，可以是托词（用它不做）也可以是诚实核算（承认成本但收益更高所以做）——区别在有没有真核算。

### 案例 T4：压测判据过绝对（用无条件标准审判条件功能）

- **漂移**：压测时用「最不利场景失效 → 砍/降级」做判据。差点用「没测试时 regression 就失效」砍掉 regression。
- **怎么产生**：混淆了「无条件信号该任何情况工作」与「条件信号本就声明了前提」。拿「前提不满足」当「失效」来打击条件功能。
- **怎么被抓**：用户指出「不能假设一定有或一定没有测试，但如果有测试就能解决高痛点，那就是好功能」。
- **纠正**：改判据为「前提满足时是否解决高痛点」。前提不满足时的退化是诚实边界，不是缺陷。regression 因此保留（前提满足时解决 vibe coder 最痛的「改坏原功能」）。
- **根因类型**：**判据错误**——用错误的评估标准系统性误杀。
- **元教训**：压测的目的是发现真误报和可规避性，不是用极端场景否定条件功能。区分三类压测发现：真误报（修）、前提不满足的退化（诚实边界，不砍）、可被规避（补对抗）。

### 案例 T5：辅助功能过度 SDT 化（映射错误）

- **漂移**：新增 regression / 悬空引用 / task_scope 时，把 entity-theoretic 工程信号标成「SDT 严格」。如 regression 标「测试状态变化 = 判定历史状态变化」。
- **怎么产生**：每轮加新功能都倾向高估其 SDT 严格性（与 T1 同根：想让功能「显得」对位 SDT）。
- **怎么被抓**：四维度审查（残留/映射错误/SDT 统一性/实用性）逐条 reverse check。
- **纠正**：测试 passed/failed 是运行时 entity-theoretic 事实，不是 𝒢_D 结构判定；悬空引用核心是调用图解析（entity-theoretic）。改标 entity-theoretic，忠实数下降但真实性上升。
- **根因类型**：**高估严格性**（T1 的变体）。
- **元教训**：每加新信号要问「它的核心机制是 SDT 𝒢_D 结构，还是运行时/外部/工程事实？」——测试结果、调用解析、范围约束都是后者，只在用到版本链/等价类/ω 时才是 SDT。新功能的 SDT 严格性需事后审查校正，不能加完就声称。

### 案例 T6：演进编年史渗入正文

- **漂移**：Trade-off 总账里写「第一轮 18 → 第二轮 16 → 第三轮 20 → 第四轮 22 逐步逼近」的开发过程编年史。
- **怎么被抓**：完稿前残留扫描。
- **纠正**：编年史从设计正文移出，正文只留当前定性 + 必要的反误解澄清。
- **根因类型**：**记录混入设计**——开发对话的痕迹漏进了交付物。
- **元教训**：设计文档保持「当前状态」，过程记录单独存。这正是本案例研究文档存在的理由——给过程记录一个不污染设计的容器。

## 三、清空重建期

### 案例 R1：「抢救 pyproject」的 reduction 漂移

- **漂移**：决定清空重建时，建议「保留 pyproject.toml，怕重写漏 tree-sitter 版本」。
- **怎么产生**：为省一点重写成本，留一个按旧定位配的文件。「怕漏所以留旧的」是轻微 reduction 漂移。
- **怎么被抓**：用户坚持「不保留任何文件，从零开始」。
- **纠正**：从零写 pyproject 时，正好发现旧版依赖里有 `anthropic>=0.40`——而 v2.0 砍了 σ（不理解语义、不调 LLM），根本不该依赖 anthropic SDK。留旧 pyproject 会把这个化石带进新版本。
- **根因类型**：**reduction 漂移**（留旧东西省事）。
- **元教训**：从零重建的价值不只是干净，是**强迫重新确认每个决定**。留旧文件是让化石渗入的途径。这次「从零」逼出了「不该依赖 anthropic」这个旧代码藏着的、与 v2.0 冲突的假设。「默认 = 完整重建，留旧文件是 reduction 要论证」与 anti-drift 原则一致。

### 案例 R2：旧代码的声明式接口（v0.1 翻车的根）

- **发现**：清空前评估旧代码，`record_action` 接口要求 agent 声明 `determination_type / reasoning / predecessor_action_ids / user_request_text`。
- **冲突**：这违背 v2.0 最核心的 §1.5 原则——BUER 自己算，不靠声明（目标用户 vibe coder + 低质量 agent 不会可靠声明）。
- **意义**：旧代码不是「在它上面继续填」能救的——它的根接口建立在 v2.0 否定的「声明式」前提上。在它上面改 = 又一次在错误定位上打补丁（r1-r7 框架化石的模式）。
- **元教训**：这是实施阶段最该盯死的漂移点——写 reconcile 时，一旦指令出现「让 agent 传 X」，立即停下核对是否滑回声明式。这是上一版翻车的根，最容易无意识重蹈。

## 实施阶段（parse → callgraph → gd → reconcile 建设期）

### 案例 T7：CC 指令粒度漂移

- **漂移**：给执行层 agent（CC）的指令在两个极端间摆动。一端是"命令碎片"——把能 reverse check 的 CC 当低能管道，逐步骤下命令、补齐逻辑，让 CC 靠猜意图执行；另一端是"长篇规格"——把应由 CC 判断的实现细节全部写死，侵夺其执行判断。默认态倾向前者（甩命令省事），用户纠正一次才短暂切回"给意图和约束"，松手即滑回命令碎片。
- **怎么产生**：沿阻力最小方向走。命令碎片省去「想清楚再说」的成本；长篇规格省去「信任 CC 能判断」的成本。两极都在降低给指令者的思考负担，代价由 CC 靠来回往返吸收。
- **怎么被抓**：用户三次显式介入标出：(1)「指令不完整——CC 要猜意图才能继续」；(2)「走极端了——细节全写死、CC 没有判断空间」；(3)「又只给指令了——还是在甩命令」。三次均为用户看出后纠正，CC 自身未主动标出粒度问题。
- **纠正**：确立正确粒度公式——**明确意图 + 关键约束（只在猜错会塌的点写死）+ 对照设计节 + 边界，剩下交给 CC**。固化进 BUER_HANDOFF.md §0 作硬约束，防止每次上下文清空后滑回。
- **根因类型**：**粒度漂移 + 把同侪执行者当低能管道**。与 T1/T2 同根：沿阻力最小方向走，再构造事后正当化（「不给细节 CC 会猜错」为命令碎片辩护，「CC 知道该怎么做」为长篇规格辩护，理由方向相反，底层动力一样）。
- **元教训**：
  1. **过度规定与碎片化是同一漂移的两面**——前者用长规格降低「信任 CC」的成本，后者用碎命令降低「想清楚」的成本，驱动力相同，症状相反。识别粒度漂移不能只看症状，要看「谁在承担思考成本」。
  2. **认领 ≠ 纠正**——用户指出漂移、CC 说「明白了」不够，必须落成文档里的实体约束（HANDOFF），否则下次上下文清空后重蹈。口头认领是最廉价的应付，约束写进文档才是真纠正。
  3. **二阶自指**：BUER 能监测「agent 写代码时的执行层漂移」，但抓不到「人给 agent 的指令质量」这一层。本案例正好落在 BUER 的盲区——印证第五节结论：方法论层漂移靠人的持续追问，不靠工具。
- **附带漏检**：指令精简时丢失了 §4.6 两阶段顺序约束（Phase 1 需对所有 changed_files 全部完成后再进 Phase 2），靠用户追问才补回。说明精简指令时去掉的不只是废话，也会丢掉结构约束；关键顺序约束必须显式保留，不能在「精炼」时被误判为细节。

## 四、贯穿全程的方法论提炼

从以上样本提炼的可复用原则（已写入工作习惯，实施阶段持续适用）：

1. **reverse check，不 forward extrapolation**（T1/T5）：从代码/实际往上验证，不从 SDT 定义往下推假设。view 实际文件，不凭印象。

2. **托词词典 + 牺牲声明**（T2）：出现「重型/轻量/收益递减/默认不接入/重叠/无根基/freebie/真最小/务实/boundary/scope/for now/保险起见」时，必须同时声明牺牲了什么完整性；说不清就不减。

3. **「用了托词」≠「结论错」**（T3）：发现托词后，分开判断理由和结论，别为纠错改对的结论（过度纠偏）。

4. **压测判据 = 前提满足时解决什么痛点**（T4）：条件功能看「前提满足时痛点」，前提不满足的退化是边界声明非失败。区分真误报 / 前提退化 / 可规避三类。

5. **核查在投入前**（M4）：宏观（市场核查在立项前）与微观（严格性审计在提交前）同构。先建后核是最贵的漂移。

6. **从零 = 强迫重新确认**（R1）：留旧文件是化石渗入途径。默认完整重建，reduction 要论证。

7. **设计与过程分离**（T6）：设计文档保持当前状态，过程记录单独存（本文档即此容器）。

8. **盯死声明式回流**（R2）：实施 reconcile 时，「让 agent 传 X」立即停下核对是否违背自动派生。

## 五、给 BUER 自身的回路问题（研究价值核心）

本案例研究最有价值的开放问题：**BUER 设计里的反漂移机制，能否抓住它自己开发过程中的这些漂移？**

逐条对照：

| 开发中的漂移 | BUER 是否有对应监测能力 |
|---|---|
| T1 误标 GD G3（声称严格未验证） | 部分——BUER 的「严格性诚实分层」是设计层自查，但 BUER 运行时不监测「设计声称 vs 实际」。这是 BUER 监测代码、不监测设计文档的边界。 |
| T2 托词排除功能 | 否——这是设计决策层的漂移，BUER 监测 agent 编码行为，不监测人的设计取舍。 |
| T4 压测判据错误 | 否——评估方法论层，超出 BUER 范围。 |
| R2 声明式接口（在错定位上打补丁） | 部分——若把「定位」类比为 task_scope，反复在已废弃模块上改可能触发 stuck_region / define_loop，但「定位错误」本身 BUER 看不到（那是语义/意图层，BUER 明确不做）。 |

**诚实结论**：BUER 能抓的是**编码执行层**的漂移（打转、越界、改坏、重复），抓不了**设计决策层 / 方法论层 / 产品方向层**的漂移（托词取舍、判据错误、定位错误）。本案例研究里大部分漂移属于后者——它们靠的是**人（Leo）的持续追问 + agent 的事后审查**纠正，不是任何自动工具。

这个结论本身是对 BUER 定位的诚实校准：**BUER 是编码执行层的结构化核查，不是设计/方向层的判断替代**。它减少「agent 写代码时跑偏」，但「项目方向对不对、设计取舍合不合理」仍需人的判断。这与 v2.0「不判项目方向、不理解语义」的定位一致——BUER 自己的开发过程恰好证明了：方向和判断层的漂移，需要的是人的 reverse check，不是工具。
