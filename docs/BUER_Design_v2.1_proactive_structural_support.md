# BUER 设计文档 v2.1 —— 主动结构支持（三个真实痛点）

> 本文档是 v2.0 的增量扩展，新增三个功能。三者共一个母题：**面对大而复杂的代码库，BUER 用结构视角帮 agent / 资深程序员聚焦到该看的小范围，精的判断留给人和 agent。** BUER 不做"全量精确答案"，做"用结构缩小搜索范围"。
>
> v2.0 已实现（L0–L3）：数据层、ω/d_J/Γ_R/连通分量、TS 类型驱动数据流档、9 信号、安全网、5 辅助、送达层。本文档新增的是在已有结构能力之上的**主动结构支持**。

---

# 0. 技术底座（已查证的 Claude Code hook 机制）

三个功能都依赖"BUER 从 agent 运行中拿什么信号、怎么把结构回应送达 agent / 用户"。以下机制经 Claude Code 官方文档查证（非假设）。

**先审准 v2.0 现状（避免在错判上设计）**：v2.0 不是"被动报警"——

| 通道 | v2.0 现状 | 机制 |
|---|---|---|
| agent 警报（两步响应第一步） | **已主动推** | post-edit 响应体（plain-text stdout）由 Claude Code 注入 agent context（server.py：response body is what curl outputs to stdout, which Claude Code injects） |
| user 升级（第二步） | **纯被动拉** | get_user_alerts MCP tool，用户须主动调才看到 —— **这是缺陷，v2.1 修** |

所以 v2.1 不是"从被动变主动"（agent 通道 v2.0 就主动）；v2.1 的"新"在：① 新触发场景（token / 向导 / 技术债）② 新 hook 时机（SessionStart / Stop，v2.0 没有）③ **修 user 通道的纯被动缺陷**。agent 通道复用已有的 post-edit stdout 注入路径，不需引入新机制。

**可用 hook 机制（查证）：**

| 机制 | 能力 | 可靠性 / 用途 |
|---|---|---|
| **PostToolUse stdout 注入** | hook 输出注入 agent context（v2.0 已用） | 可靠。agent 警报 + 向导建议 + token 预警转告用户的**主渠道** |
| **PostToolUse matcher: Read/Grep/Glob** | 可 hook 只读工具 | **搭扫库车**——扫描是读操作 |
| **SessionStart** | 会话开始注入 context | 粗层结构地图常驻 |
| **Stop / SubagentStop** | agent 完成响应时触发一次 | 重分析（全库建图）；**user 级警报一轮结束汇总推送** |
| **Notification hook + 桌面通知** | 系统级桌面通知（osascript / 跨平台） | opt-in，最强打断，高优先级预警可弹到用户眼前 |
| **systemMessage** | 显示给用户 | **不可靠**——VS Code 不渲染（#15344）、部分版本 Stop hook 不显示（#50542）、SDK 文档自警"may not appear in all output modes"。**不单用，仅作 Stop 汇总的附带** |

**主动通知用户的多渠道设计（修 user 纯被动缺陷）**：升级到用户的警报（第二步）和 token 浪费预警，价值在"及时让用户知道"，等用户调 get_user_alerts 才看到太晚（用户不知道要拉）。故 user 通道改为**主动为主、被动为辅**：

1. **agent 转告（主渠道，最可靠）**：user 级警报**也注入 agent context**（复用已验证的 post-edit stdout 注入），让 agent 在对话里自然转述给用户（"BUER 提示你在这块投入 N 轮了，可能在浪费"）。走已验证通道，不依赖不可靠的 systemMessage。
2. **Stop hook 汇总（及时性兜底）**：agent 一轮响应结束，Stop hook 把本轮累积、未送达的 user 级警报汇总输出（systemMessage + stderr 双写，哪个 work 显示哪个），保证"一轮结束用户能看到"，不靠主动拉。
3. **桌面通知（opt-in，最强打断）**：高优先级（如 token 浪费）可 opt-in 配 Notification/Stop hook 触发系统桌面通知。opt-in（非所有人想要弹窗）。
4. **get_user_alerts（保留为补充）**：随时主动拉全部历史警报——从"唯一通道"降级为"查历史的补充"，不再是用户获知警报的唯一途径。

**关键约束（硬，查证得到）：PostToolUse hook 同步执行，慢则阻塞 agent（建议单次 <5s）。重分析（全库建图、跨文件 TS 数据流）绝不在每次 post-edit 同步跑——挪到 Stop / SessionStart，或异步。**

这把架构天然分成**三层按 hook 生命周期分布**，正好贴合"分层 zoom"：

```
SessionStart   → 粗层（连通分量概览）常驻注入            —— 一次，廉价
PostToolUse    → 轻量信号 + 局部建议（stdout 注入，v2.0 已用）—— 每次编辑，必须快
Stop/Subagent  → 重分析（全库建图、TS 数据流、结构刷新）  —— 完成时一次
```

**matcher 隔离已知 bug**（anthropics/claude-code#20334）：PostToolUse 配特定 matcher 仍可能对其他工具触发。所有新 hook 脚本必须能优雅处理非目标工具输入（沿用 post-bash 已有的"非目标静默放过"模式）。

# 1. Token / 成本浪费预警

## 1.1 真实痛点（数据）

成本是 AI 编码最响亮的抱怨：Claude Code 重度使用每开发者每月 150–200 美元、计费不透明（开发者被账单惊到、不懂一次 session 为何烧那么多 token）；有真实案例"老板花约 5500 美元 Cursor 额度 vibe coding，底下全是 bug 和 AI slop"。用户的崩溃是"花了钱得到 slop"。

## 1.2 BUER 怎么解（不是新检测，是新呈现 + 新阈值）

BUER 已经检测"不收敛"（stuck_region / debug_loop）。缺的是把它翻译成用户真正痛的度量——**浪费**。用户不关心"版本链长度 ≥5"，关心"我在这块烧了多少、值不值得继续"。

**核心：BUER 看不到真实 token / 美元（在 CC / Cursor 计费里，不在编辑事件里）。用结构代理。** 诚实标这个边界：这是"投入量 vs 收敛"的代理预警，不是账单。

**投入度量（结构代理）**：某 region（define 或其影响域）上累积的——
- 编辑轮数（version_chain 长度）
- 时间跨度（determinations 时间）
- 反复触发的信号数（同 region 多个 stuck / debug incident）

**触发判据**：现有 stuck_region 在 θ₁=5 轮报"打转"。token 预警是**更高投入阈值**的升级——同一 region 累积编辑轮数 ≥ THETA_WASTE（初值 15，待校准）**且**跨越多个 stuck / debug incident 仍未收敛 → 升级的、面向用户的预警。

**投入度量是否结合影响域大小（待校准时定）**：纯编辑轮数 vs 编辑轮数 × 影响域大小（在大 define 上折腾比小 define 更费）。初版用纯轮数 + 时间跨度，影响域加权留校准期评估。

## 1.3 送达（用查证的机制，主动为主）

token 浪费预警是**给用户**的（"该不该停"是用户的成本判断），且要及时（花太多之前）。用 §0 的多渠道主动通知，不靠用户主动拉、不单靠不可靠的 systemMessage：

- **主渠道：agent 转告**——预警注入 agent context（post-edit stdout，已验证），agent 在对话里转述给用户："你在 validate_token 这块已投入 N 轮编辑 / M 时间仍未收敛，继续可能是浪费，建议停下人工介入。"
- **及时兜底：Stop hook 汇总**——一轮结束若有未送达的浪费预警，Stop hook 输出给用户。
- **可选强提醒：桌面通知**——token 浪费是高优先级，可 opt-in 桌面通知弹到用户眼前。
- 检测在 post-edit（轻量，只查累积计数 + 比阈值，快，不违反 <5s）；送达走上述通道。

## 1.4 克制（守定位）

**不替用户决定"该不该停"**（那是用户的成本 / 价值判断），只给"投入了多少 vs 收敛没有"的事实。措辞建议、疑问，不强制。

## 1.5 与现有信号的关系

token 预警**复用** stuck_region / debug_loop 的检测，是它们的"投入维"升级呈现，不是独立检测器。stuck_region 报"结构打转"（给 agent，第一步），token 预警报"投入浪费"（给用户，升级）——同一现象，两个受众、两个阈值、两种呈现。

## 1.6 SDT 地位

投入度量是工程代理（编辑轮数 / 时间），无 SDT 对位。stuck_region / debug_loop 的不收敛检测本身的 SDT 依据见 v2.0 §2.2 / §3。

# 2. 大型代码库结构向导（分层 zoom）

## 2.1 真实痛点（数据）

agent 在大型 / 陌生代码库里失控：Cursor 没法重构 18000 行 Node API、agent 编排出错。根因常是 **agent 没有全局结构感**——只能局部看文件，缺"这库分几块、枢纽在哪"的骨架。BUER 的 𝒢_D 恰好是全局结构。

**受众：agent + 资深程序员。** **准确性是硬要求——错的结构地图比没有更糟（误导）。这对横向关系质量提出严格要求（见 §2.6）。**

## 2.2 核心设计：分层 zoom（Google Maps 模型）

**不可能也不必要为十万行代码生成全量详图然后维护**——代价爆炸、绝大部分详情用不到、维护不可持续。像地图一样**分层，只在需要时 zoom in 做局部详图。**

𝒢_D 上的横向关系本就有天然缩放层级，不用额外造：

| 层级 | 内容 | 计算 | 维护 |
|---|---|---|---|
| **粗（大陆）** | 连通分量 = 相互因果独立的功能子系统 | 需**新增全局划分**（见下） | **常驻**（SessionStart 注入） |
| **中（城市）** | 某连通分量内的 hub 节点（高 ω/Γ_R 度数枢纽） | 进入该分量时算 | 按需，用完即弃 |
| **细（街道）** | 某 define 的改动前局部简报 | 即时算这一个 | 按需，用完即弃 |

**核实现状**：buer 现有 `connected_component(v)` 是**单点查询**（给定节点 v 返回 v 所在的分量），不是"把整库节点划分成 N 个分量"的全局划分。粗层地图需要全局划分——这是**需新增的函数**（遍历所有节点并查集分组），不是复用现有单点版。诚实标：粗层不是"已有能力的呈现"，含一个新增的全局连通分量划分。

**关键：BUER 不维护整库详图。常驻的只有最粗层（连通分量划分）。中层、细层都是 query-driven、lazy、用完即弃**——agent zoom 到哪才算哪，算完不长期维护。被改动影响的那块变了，只重算那一小块，不是全图。

这解决三个问题：不全量（只常驻粗层）、代价可控（细节 lazy，只算当前 zoom 的局部）、无冗余（不预生成用不到的详情）。

## 2.3 三个交互形态

### 形态 A：粗层全局地图（SessionStart 常驻）
会话开始，BUER 通过 SessionStart hook 注入粗层概览：这库分几个连通分量（功能子系统）、各分量的规模、跨分量的枢纽。给 agent "这库的骨架长这样"，不含分量内详情。

### 形态 B：改动前局部简报（PostToolUse / query-driven）
agent 要改某 define 时，即时给这一个的结构上下文：谁依赖它（blast_radius，改了波及谁）、它依赖谁（callees，理解它先看哪些）、和它共享历史 / 下游的（ω/Γ_R，相关功能区）、所属连通分量（哪个子系统）。给 agent 一张局部地图，省去在大库里瞎摸。

### 形态 C：过程中的结构性建议（搭扫描的车，渐进式）
**这是最关键也最需要克制的形态。** 见 §2.4 时机。

## 2.4 形态 C 的介入时机（关键设计：过程中，不是开场）

**编程 agent 有自己的扫描方式。BUER 不在一开始介入指导——那既不必要（agent 有自己的章法）也不准确（开场 BUER 没图，只能给空泛方法论 = 噪音）。**

**正确介入：过程中。** agent 用自己的方式扫库（读操作），BUER 搭车边看边增量建图，**等图积累到足够结构、能给出准确的具体建议时才介入**——给的是"基于已发现结构的具体建议"（"你扫的这块里，X 是高连接枢纽，很多地方依赖它，值得重点理解"），不是"应该先看枢纽"的空泛方法论。

**介入条件 = 结构清晰度阈值**（图够大、枢纽够明显），不是时间点、不是开场。在那之前 BUER 安静建图，不出声。

这与 BUER 一贯的克制一致：**它不抢 agent 的活（扫描是 agent 的事），在自己真有东西可说时（图够了）才补一句结构视角**——和别的信号一样，观察到足够信息才发声。

**BUER 是过程中的结构副驾，不是开场的领航员。** agent 开车（扫描），BUER 看路（建图），看清了才提醒一句"前面那个路口很多路汇过来，注意"，不在发车时规划路线。

## 2.5 搭扫描车的机制（查证）

- agent 扫库 = 大量**读**操作（Read / Grep / Glob）。BUER 加 PostToolUse matcher = Read / Grep / Glob 的 hook，搭车收到"agent 读了哪些文件"信号 → 增量建图。
- 注意 matcher 隔离 bug（#20334）：hook 脚本优雅处理非目标工具输入。
- 读操作 hook 必须**极轻**（每次读都触发，<5s 约束最紧）：post-read 只记录"读了哪个文件"+ 触发增量建图入队，**不在 post-read 同步跑重分析**。重的全库建图 / 数据流放 Stop hook。
- 介入（形态 C 的建议）通过 PostToolUse stdout 注入（复用 v2.0 agent 注入路径）——但仅当结构清晰度阈值达到，否则空输出（不打扰）。

## 2.6 准确性要求（你强调的硬约束）

向导是**主动断言**"这是地图 / 这是枢纽 / 改这里波及这些"——错了是误导，比不给更糟。这对横向关系质量是**质量要求的跃升**（v2.0 横向关系只被动用于 debug 根因，错了用户少个参考；向导错了直接误导）。

**质量依赖**：
- 连通分量划分的正确性 —— 本该一块的分成两块、或本该独立的连一起，整个 zoom 地图基础就错。连通分量依赖 𝒢_D 边的完整性。
- 跨 define 边覆盖率 —— 动态语言（Python / JS）漏边多，连通分量可能误分（漏边 → 本该连通的被分开）。TS（数据流档）覆盖率高。

**诚实边界（必须标）**：向导对静态类型语言项目（TS / TSX，数据流档高覆盖）准确度高；对动态语言项目（Python / JS，调用图档漏边）准确度打折，连通分量可能误分。**向导的准确性 = 横向关系覆盖率，覆盖率是前提不是保证。** 在动态语言项目里，地图标注应附"基于已检测到的依赖，可能有未检测到的连接"。

## 2.7 一次性建图成本（诚实）

粗层（连通分量）需要先有整库 𝒢_D 边才能分量。建整库 𝒢_D 边（尤其跨 define 数据流）对十万行是**一次性大开销**。这个成本跑不掉（任何要给全局视角的工具都得先看一遍全库）。缓解：
- 只建一次，之后增量更新被改动的局部（不重建全图）。
- 连通分量只需边的连通性（不需每条边精确），可用较便宜精度建图。
- 放 Stop hook（不阻塞编辑）/ 搭 agent 首次扫库的车渐进建。

## 2.8 SDT 地位

连通分量（GD Prop 9.2）、ω（Math Ext §11.1b）、Γ_R（GD Def 7.1）、blast_radius 均为 v2.0 已实现的严格结构运算。向导是这些运算的**主动呈现 + 分层组织**，无新 SDT 概念。

# 3. 技术债：结构关注点提示（给范围，不判断）

## 3.1 真实痛点（数据）

维护挑战和技术债（"AI slop 累积"）是 vibe coding 的明确代价；"底下全是 bug 和 AI slop"。

## 3.2 BUER 的定位（关键：发现并建议关注，不解决、不判定）

**BUER 不判定"这是技术债"，不找 bug。它圈一个"值得关注的结构范围"，交给 agent / 用户针对性验证。** 范围越小，agent 验证成本越低——这就是价值：agent 面对十万行不知从何查起，BUER 说"这几个 define 结构上是高耦合枢纽 / 被反复改动的区，建议重点看看有没有问题"，agent 只需验这一小块，不用扫全库。

**BUER 提供"往这看"的结构指针，不是"这里有债"的结论。** 精的判断（是不是真有 bug、是不是真该重构）留给 agent / 用户。

这与大库向导是同一思路的两面：都用结构把注意力**聚焦到小范围**，精的判断留给人 / agent。

## 3.3 SDT 依据（结构耦合负载）—— 现状核实

SDT 本体有 **constraint-load accumulation Λ(v)**（GD Cor 6.6a / Thm 6.7）：节点 v 的祖先锥里所有产物的累积约束负载，链越长、独立分支汇聚越多 Λ 越大 → 下游可能性空间 A 被压缩越狠（A 收缩不可逆，Thm 10.5a）。结构同构强：一个 define 依赖历史越长、汇聚分支越多 → 可改动空间越小、改它越牵连，正是技术债"改不动、一动连锁"的体感。

**但核实 buer 代码：Λ 在 buer 尚未实现**（buer 现有的是 ω/d_J/Γ_R/连通分量，无 Λ 计算）。所以技术债功能有两条路：

- **路 A（推荐，用 buer 真有的）**：耦合度量 = buer **已实现**的量的组合——blast_radius（caller 数，已实现于 assists.py）+ callees 数（依赖出度，调用图已有）+ version_chain 长度（反复改动，已实现）。这些直接可用，不需新实现。Λ 作为"完整版"留后续，初版用这三个已有量近似"结构耦合 + 改动频度"。
- **路 B（完整）**：在 𝒢_D 上实现 Λ(v) = 祖先锥产物加权计数（GD Thm 6.7），作为新结构运算。更贴本体，但是新工作（不是复用）。

**初版走路 A**：技术债关注点用 blast_radius + callees + version_chain 三个已实现量，**不声称实现了 Λ**——诚实标"基于已有耦合/频度量近似，非 SDT Λ 完整实现"。

**仍须诚实地小（避免拿单一结构量当复杂现象）**：
- 只覆盖技术债的**耦合 + 改动频度维**，不碰重复 / 命名 / 复杂度 / 语义债。
- BUER 的 𝒢_D 是**编辑历史图**，version_chain 长 ≠ 债重（改得多的干净代码也长）。**因为 BUER 只"给范围让 agent 验"、不"判定债"，这不构成误判**——"改得多 / 耦合重"本身就值得关注，验出没问题也正常。
- 动态语言漏边 → 低估耦合，TS 可靠（同 §2.6）。

## 3.4 形态：结构关注点提示

基于 buer 已实现的结构信号（高 blast_radius / 高 callees 出度 / 反复改动 version_chain 长）圈出"建议关注的 define 范围"，措辞："这块结构上是高耦合枢纽 / 被反复改动，建议关注下是否有需要重构或修复的地方。"**给范围，不给判断。** agent 拿这个小范围针对性验证，成本远低于扫全库。

**命名：不叫"技术债检测"，叫"结构关注点 / 高耦合枢纽提示"**——它借 SDT 的 Λ / A 收缩做结构依据，明确标"这是技术债的耦合维，非全部；不碰语义债；给范围不判断"。

## 3.5 送达

- 给用户 / agent：低优先级提示，附在 project_overview / 向导里（不是打断式警报——技术债关注点不要求及时性，"有空看看这块"）。
- 不进 incidents 状态机（它不是坏行为警报，是关注建议）。归辅助 / 向导附带信息。

## 3.6 SDT 地位

Λ（GD Cor 6.6a / Thm 6.7）是严格 SDT 结构，但 **buer 尚未实现 Λ**。初版（路 A）耦合度量用 buer 已实现的 blast_radius + callees + version_chain，**借 Λ 的结构直觉命名，但不是 Λ 的实现**（诚实标，同 v2.0 对 node_fingerprint↔§2.4.4 的降级处理）。Λ 完整实现留路 B 后续。

# 4. 实施计划

## 4.0 共同前置：hook 生命周期三层 + 新端点

三个功能共享的基础设施，先做：

**新增 hook 端点（server.py）**：
- `/buer/session-start`（SessionStart）：注入粗层结构地图。
- `/buer/post-read`（PostToolUse matcher Read/Grep/Glob）：搭扫描车，极轻，只记读 + 入队增量建图。
- `/buer/stop`（Stop / SubagentStop）：触发重分析（全库建图刷新 / 连通分量重算）。
- 现有 `/buer/post-edit` 的 stdout 注入路径（v2.0 已用于 agent 警报）**复用**于主动注入向导建议 / token 预警 / user 转告——不新增机制，扩展注入内容。

**约束落地**：post-read / post-edit 必须快（<5s）——只做轻量查询 + 入队，重分析全部在 stop。建一个"待重算队列"，post-read/edit 入队，stop 出队执行。

**注意 Stop hook 也是同步的**：一次性全库建图（十万行可能数十秒）若在单次 Stop hook 同步跑，会卡住 agent 一轮结束。故大建图必须**后台异步**（Stop hook 只触发建图任务并立即返回，不等完成；建图在独立进程 / 线程跑，完成后结果可用）或**分批**（每次 Stop 推进一部分）。Stop hook 返回要快，重活异步化——与 <5s 约束一致，非例外。

**hook_setup.md 更新**：新增 SessionStart / Stop / Read hook 配置（标注哪些 opt-in）。

## 4.1 实施顺序（深度优先 + 依赖序）

```
批次 1（前置）：hook 三层基础设施
  - server.py 新增 session-start / post-read / stop 端点

  依赖：无（纯接口扩展）

批次 2：Token 浪费预警（最成熟，基于已验证的 stuck/debug）

  - THETA_WASTE 阈值（初值 15）+ 升级判据
  - systemMessage 送达用户（经 post-edit 返回）
  依赖：批次 1 的 stdout 注入（agent 转告）+ Stop 汇总 + 可选桌面通知

批次 3：大库向导
  3a 粗层全局地图（连通分量概览，SessionStart 注入）

  3c 过程中结构建议（搭扫描车 + 结构清晰度阈值介入）

  - 关注点范围圈定 + "给范围不判断"措辞
  - 附在 overview/向导（不进 incidents）
  依赖：批次 3 的横向关系组织（同结构基础）
```

## 4.2 校准依赖（诚实）

token 预警的 THETA_WASTE、技术债的耦合阈值、向导的结构清晰度阈值——**均为初值，需真实数据校准**（同 v2.0 的 ~15 个待校准阈值）。这些功能可落地（机制 + 判据齐备），但阈值要真实大库 / vibe 项目跑 BUER 才能调准。校准依赖真实使用，不依赖功能开发。

## 4.3 每批次的验证要求

每批次落地后，按 v2.0 三层审计标准核：
- 代码↔设计：判据 / 阈值 / 送达照本设计。
- SDT 对齐：Λ / 连通分量 / ω/Γ_R 严格性（读本体核，不读转引）；诚实标注（耦合维非全部、向导覆盖率边界、投入度量是代理非账单）。
- R2 红线：新 hook（post-read / session-start / stop）的输入是 agent 运行的客观事实（读了哪些文件、会话开始 / 结束），非 agent 声明结构元数据。**post-read 收的是"读了哪个文件"（事件事实），不是 agent 申报"这文件是枢纽"。**
- hook <5s 约束：post-read / post-edit 不跑重分析（验证重活在 stop）。

## 4.4 明确不做（边界）

- BUER 不主动跑测试 / 不自己扫库（搭车，不抢 agent 的活）。
- 不判定技术债 / 不找 bug（给范围让 agent 验）。
- 不维护全库详图（分层 lazy）。
- 不在开场指导扫描（过程中、有依据才介入）。
- token 预警不报精确美元（结构代理，非账单）。
- 不替用户决定停 / 继续（给事实，不给决定）。

# 5. 与 v2.0 的关系

本文档新增的三个功能全部**建立在 v2.0 已实现的结构能力之上**（ω/d_J/Γ_R/连通分量/blast_radius/Λ/stuck/debug），不引入新的 SDT 概念，引入的是：
- 新的 **hook 生命周期机制**（SessionStart / Stop / Read）——查证的 Claude Code 能力；agent 注入复用 v2.0 已有的 post-edit stdout 注入路径。
- 新的**交互模式**：v2.0 的 agent 通道已是主动注入；v2.1 扩展为更完整的主动结构支持（粗层常驻 + 过程中介入 + query-driven zoom + 修 user 通道纯被动缺陷）。
- 一致的**母题与克制**：用结构缩小范围，精判断留给人 / agent；搭车不抢活；有依据才发声；给范围 / 方向不给结论。

v2.0 的所有定位约束（不懂语义、纯结构、R2 红线、诚实标注降级、不对称忠实）在本文档全部继承。
